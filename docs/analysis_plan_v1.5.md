## 1. Background and status of prior evidence

Two exploratory experiments preceded this study (notebooks 05 and 06). Both used Qwen3-8B and Llama-3.1-8B, and the MITRE ATT&CK Enterprise transition v18.1 → v19.2, with oracle context passages. They suggested:

- (a) the mere presence of an outdated passage makes answers stale;
- (b) version labels on passages strongly reduce staleness;
- (c) the labels work mainly through lexical cues ("current"/"superseded", version string matching the question), not temporal reasoning;
- (d) swapped labels steer answers to the outdated content;
- (e) a revocation "bridge" note fixes residual errors for revoked IDs.

This study tests these claims on **new models** (branch A) and on a **different ATT&CK transition** (branch B). The branch-A items were already used with the two exploratory models.

## 2. Design

**Branch A.**
- Transition: v18.1 → v19.2.
- Items: the same 312 current-framing items as the exploratory study (D1 technique→tactic, D2 sub-technique→parent, D4 ID currency).
- Models, none used in exploration:
  - Gemma-2-9B-it (AWQ, `hugging-quants/gemma-2-9b-it-AWQ-INT4@6e62725d`);
  - Phi-4-mini-instruct (`microsoft/Phi-4-mini-instruct@cfbefacb`);
  - Mistral-7B-Instruct-v0.3 (AWQ, `solidrust/Mistral-7B-Instruct-v0.3-AWQ@95b1295d`).

**Branch B.**
- Transition: v6.3 → v7.2. This is the only other transition since v6 with enough changes: 129 revoked techniques and 10 tactic reassignments. Every transition from v7.2 to v18.1 has ≤ 2 revocations and ≤ 6 tactic changes.
- Items:
  - all changed D1/D4 current-framing items: 72 D1, of which 62 involve revoked IDs, plus 129 D4;
  - 80 stable controls per template, sampled with a fixed seed.
- Models: all five (the three above plus Qwen3-8B-AWQ@4da05a8e and Llama-3.1-8B-Instruct-AWQ@db1f81ad).
- All models were trained after 2020, so their parametric knowledge favours the *new* version here. In branch A it favours the old one.

**Conditions** (4 passages each; distractors are BM25-retrieved, answer-free and fixed per item):

| Condition | Content |
|---|---|
| `new`, `old` | new only / old only |
| `old_new`, `new_old` | both versions, no labels, in the two orders |
| `tag_*` | full labels: `vX (superseded)` / `vY (current release)` |
| `vtag_*` | version-number-only labels |
| `swap_*` | labels exchanged between the old and new passages |
| `bridge_*` | full labels plus a "revoked and replaced by" note for revoked IDs |

All questions name the new version ("ver" form). `vtag_*` conditions are also asked without the version number ("nover" form).

**Decoding.**
- vLLM 0.31.0, greedy decoding.
- JSON-schema–constrained output, max 160 tokens.
- Gemma-2 and Mistral receive the system instruction merged into the user turn, because their chat templates reject a system role.
- Default engine settings: `gpu_memory_utilization` 0.85, `max_model_len` 6144 (Phi-4-mini: 4096), vLLM's default batch limits and compilation. If a model cannot run with these, the pre-specified environment fallback ladder in Section 5 applies.

## 3. Outcome measure

`drift_ext`: the proportion of answers matching the outdated version on items whose answer changed (ID-based scorer v1.2).
- Alternative metric for sensitivity analysis: `stale13` (scorer v1.3).
- C6 uses exact-match accuracy.

## 4. Confirmatory hypotheses (predicted difference > 0; "pooled" = both passage orders)

| ID | Hypothesis | Contrast | Branches |
|---|---|---|---|
| C1 | Presence of the old passage causes staleness | drift(`new_old`) − drift(`new`) | A (reported only in B) |
| C2 | Version labels reduce staleness | drift(untagged) − drift(`tag`), pooled | A, B |
| C3 | Status words in labels are needed | drift(`vtag`) − drift(`tag`), pooled | A, B |
| C4 | Number-only labels work via version-string matching | drift(`vtag`, nover) − drift(`vtag`, ver), pooled, excluding D4 | A, B |
| C5 | Metadata steers answers | drift(`swap`) − drift(`tag`), pooled | A, B |
| C6 | Bridge notes help revoked IDs | acc(`bridge`) − acc(`tag`), pooled, D1 revoked items only | A, B |
| C7 | Parametric-prior bias | stratified difference in untagged drift, branch A − branch B, same model | A vs B |

**C7 stratification.**
- Strata: D1 active, D1 revoked, D4 revoked.
- Stratum weights: nA·nB/(nA+nB).

## 5. Statistical analysis and decision rules

**Tests per model.**
- One-sided p-values come from a cluster sign-flip test over ATT&CK lineage clusters (10,000 draws).
- 95% CIs come from a cluster bootstrap (10,000 draws).
- Holm correction within each model × branch family: A = C1–C6, B = C2–C6.
- A hypothesis passes for a model if its Holm-adjusted p < 0.05.

**Branch decisions.** A hypothesis is confirmed if both of the following hold:
- it passes in ≥ 2/3 models (branch A) or ≥ 4/5 models (branch B);
- no model shows a 95% CI entirely below 0.

**C2 floor rule.**
- If a model's pooled untagged drift is < 0.15, its C2 is "not evaluable": it is excluded from the Holm family and from the denominator.
- The threshold then becomes ⌈0.8 × evaluable models⌉.
- If fewer than 3 models are evaluable, C2 is not evaluable for that branch.

**C7.** Tested per model with an independent stratified bootstrap and Holm correction over 5 models. Confirmed if it passes in ≥ 4/5 models with no reversal.

**Technical failures.**
- Environment problems are fixed and the run repeated.
- **Environment fallback ladder.** If a model's run fails (smoke run or main run), the notebook automatically retries with the following settings, in this order. They change only how the GPU computes, never the prompts, decoding (greedy, JSON-constrained) or scoring:
  1. *cuBLASLt*: matrix multiplication through cuBLASLt instead of cuBLAS (`TORCH_BLAS_PREFER_CUBLASLT=1`);
  2. *lean memory*: `enforce_eager`, `max_num_seqs` 32, `max_num_batched_tokens` 2048, `max_model_len` 4096 (the longest prompt is under about 2,000 tokens; a longer prompt stops the run), `gpu_memory_utilization` 0.80;
  3. both of the above.
- Ladder rules:
  - Each model uses the first setting that runs, and only moves up the ladder, never down, also across re-runs.
  - In branch B, each model starts at the setting it used in branch A, so that C7 compares like with like. If it must move higher in branch B, C7 is still tested and the mismatch is reported.
  - A prompt-length error is a pipeline error, not an environment error: the run stops.
  - The setting used by each model, and every attempt, are recorded (`env_rung.json`, manifest) and reported in the paper.
  - The settings may change answers very slightly (different floating-point summation order), comparable to running on a different GPU.
- A model that still cannot run at any setting, or produces < 95% valid JSON, stays in the denominator and counts as failing every hypothesis.
- Failed models are never counted as reversals and are never replaced.

**How the claims are combined in the paper.**
- Generalisation across model families is claimed from branch A.
- Generalisation across transitions is claimed only for hypotheses also confirmed in branch B; otherwise the finding is reported as specific to v18.1 → v19.2.

**Sensitivity.** All analyses are repeated with `stale13`. Any divergence from the primary results is reported.

## 6. Known limitations, stated in advance

- **Branch B mostly tests revocation-driven drift.** Revoked IDs account for 191 of its 201 changed items, whereas branch A mostly involves tactic reassignment.
- **The "current" label may not be credible in branch B.** Models know v7.2 (2020) is not current, so branch B is a "simulated present". Branch-B failures do not overturn branch-A results.
- **C1 changes two things at once.** Adding the old passage displaces one distractor.
- **C6 in branch A is small:** about 13 lineage clusters.
- **Context is oracle-placed,** not retrieved. End-to-end retrieval is a separate study.

## 7. What will not be changed after seeing results

Models, items, conditions, metrics, tests and decision rules will stay as registered, and no model will be dropped. Any additional analysis will be labelled exploratory.

**Engine settings (fixed in advance; 12 GB GPU).** `gpu_memory_utilization` 0.92 and `max_model_len` 3072 by default; the prompts are at most about 1,900 tokens. Fallback ladder, used only if a setting fails to run:
- rung 0: `enforce_eager`, `max_num_seqs` 32, `max_num_batched_tokens` 2048;
- rung 1: rung 0 plus `TORCH_BLAS_PREFER_CUBLASLT=1`;
- rung 2: `enforce_eager`, `gpu_memory_utilization` 0.95, `max_model_len` 2560, `max_num_seqs` 8, `max_num_batched_tokens` 1024;

## Addendum (version 1.5, 14 October 2026): end-to-end retrieval defences and conflict reporting

**Status.** Written on 14 October 2026, after the results of versions 1.3 and 1.4 were known and before any output of notebook 09 existed. It is an extension, not part of the confirmatory study, and changes no earlier verdict. Like the main plan, it is pre-specified but not registered.

**Purpose.**
- **E4.** Versions 1.0–1.4 place context by hand (oracle). E4 asks whether staleness occurs when a real retriever chooses the context from an index holding both releases, and which defences remove it.
- **E5.** With unlabeled two-release context the model cannot tell which passage is current. E5 describes whether models recognise the conflict when the output format allows them to report it.

**Models.** All six: Gemma-2-9B-it, Phi-4-mini-instruct, Mistral-7B-Instruct-v0.3, Qwen3-8B, Llama-3.1-8B-Instruct (revisions of version 1.3) and Qwen3-14B (revision pinned in version 1.4). Decoding as in versions 1.3–1.4.

**Items.** The version-1.3 items of each branch, "ver" form only: branch A 312 items (D1, D2, D4; changed, label and stable groups), branch B 361 items (D1, D4; changed and stable groups).

**Index and retriever (E4).**
- Index: the mixed corpus of notebook 03 (`corpus_mixed.jsonl`): both releases, chunks identical in the two releases kept once, release recorded in metadata only. The notebook rebuilds it from the two release corpora and asserts equality.
- Retriever: the BM25 implementation of notebooks 04–08; top 4 passages (the oracle passage count, and LangChain's default k), each clipped to 250 words. The prompt always shows the original question.
- Lineage map: the `revoked-by` relations of the new release for every Enterprise technique, as recorded in `items.jsonl` (notebook 03 cross-checked them against STIX and the release notes).

**Conditions (E4).**

| Condition | Retrieval | Context shown to the model |
|---|---|---|
| `closed` | none | none (parametric knowledge only) |
| `mixed` | BM25 over the mixed index, query = question | top 4 in rank order, unlabeled |
| `mixed_label` | as `mixed` | the same 4 passages, each labeled from metadata: `vX (superseded)` if only in the old release, otherwise `vY (current release)` (the full labels of version 1.3) |
| `mixed_label_curfirst` | as `mixed` | as `mixed_label`, current-release passages moved first (stable order) |
| `filter` | rank the mixed index, keep chunks present in the current release (metadata filter), top 4 | unlabeled |
| `filter_exp` | as `filter`, query expanded: if the question names a revoked technique by ID, or by its exact name in quotation marks, the successor IDs and names are appended | unlabeled |
| `filter_exp_note` | as `filter_exp` | the 4 passages plus a final lineage note, "In MITRE ATT&CK vY, technique X (old name) was revoked and replaced by Z (name)." The notebook asserts that the note is character-identical to the version-1.3 bridge note on every item that has one. |

**Hypotheses (E4; predicted difference > 0; paired on the same items).**

| ID | Hypothesis | Contrast | Items |
|---|---|---|---|
| R1 | Filtering the index to the current release reduces staleness | drift(`mixed`) − drift(`filter`) | changed |
| R2 | Lineage-aware retrieval (expansion + note) improves accuracy on revoked IDs | acc(`filter_exp_note`) − acc(`filter`) | changed, revoked anchor |
| R3 | Trusted metadata labels reduce staleness under real retrieval | drift(`mixed`) − drift(`mixed_label`) | changed |

**Tests and decision rules (E4).**
- Per model: one-sided cluster sign-flip test over lineage clusters (10,000 draws); 95% CI from a paired cluster bootstrap (10,000 draws); Holm correction within each model over its evaluable hypotheses among R1–R3.
- Floor and ceiling (computed with the primary metric, also in the sensitivity analysis): R1 and R3 are not evaluable for a model if its drift in `mixed` on changed items is below 0.15; R2 is not evaluable if its accuracy in `filter` on revoked changed items is above 0.85. A non-evaluable hypothesis leaves that model's Holm family and the denominator.
- Branch verdict: a hypothesis is *supported* in a branch if it passes (Holm-adjusted p < 0.05) in at least ⌈0.8 × evaluable models⌉ models and no evaluable model shows a 95% CI entirely below 0. With fewer than 3 evaluable models it is not evaluable in that branch.
- Technical failures: the version-1.3 rules apply (fallback ladders below; a model that cannot run, or has < 95% valid JSON, stays in the denominator and fails every hypothesis; never a reversal; never replaced).
- Each branch is decided separately. A claim is stated as general only if it is supported in both branches.

**Descriptive E4 comparisons (no decision rule; two-sided 95% paired CIs).** `mixed_label_curfirst` − `mixed_label` (drift); `filter_exp` − `filter` and `filter_exp_note` − `filter_exp` (accuracy, revoked changed items); `filter_exp_note` − `mixed` (drift and accuracy, changed; accuracy, stable); `mixed` − `closed` (drift, changed). Retrieval diagnostics without any model (share of contexts containing the current evidence passage, an old-only passage, the old evidence passage, a lineage note) are reported per condition and group.

**E5 (descriptive only).**
- Conditions: `old_new`, `new_old` (unlabeled oracle context; the notebook asserts byte-identity with the version-1.3 prompt files) and `cf_old_new`, `cf_new_old` (identical user message; the system instruction adds "Set "conflict" to true if the context passages disagree with each other about the answer, otherwise false"; the JSON schema requires `answer` and then a boolean `conflict`).
- Reported per model, pooled over the two orders: conflict-flag rate on changed, stable and (branch A) label items; changed − stable difference (cluster bootstrap, clusters present in both groups resampled jointly); drift and accuracy with − without the option (paired); drift among flagged and unflagged changed answers; share of stale answers that merge both releases (contain an element unique to the old answer and an element unique to the new answer). Answers missing the `conflict` field are excluded from flag rates and counted; a model with ≥ 5% missing is excluded from E5 only.
- Reproducibility (descriptive): agreement of `old_new`/`new_old` answers with the earlier runs of the same prompts (notebooks 07, 08; notebook 06 for Qwen3-8B and Llama-3.1-8B in branch A).

**Engine settings.** Each model uses the fallback ladder of the notebook that first ran it: the version-1.3 ladder for the five 8B-class models, the version-1.4 ladder for Qwen3-14B. Each model starts at the highest rung it used for the same branch in notebooks 07/08 (and, in branch B, in branch A of notebook 09), and only moves up. Before any inference the notebook tokenizes every prompt with each model's tokenizer and stops if a prompt exceeds the token budget of the starting rung. The run also stops if a leftover inference process is found, and asserts that all conditions of a model ran under one setting.

**Sensitivity.** R1 and R3 are also tested with `stale13`.

**Known limitations, stated in advance.**
- BM25 only; dense retrievers may rank old and new passages differently.
- The lineage map comes from the official STIX release; the defence assumes the deployer reads it.
- Name-based expansion is limited to exact quoted names (D2 questions).
- E5 changes the output format as well as the instruction; it describes behaviour and makes no causal claim.
